# PRCritiq 0.1.0

PRCritiq's first release is an evidence-backed pull request reviewer. It reads a GitHub pull request and parses every patch. It decides which changed files are safe and worth reviewing, gathers related code and static-analysis evidence, and drafts findings with a LangGraph review loop. A deterministic critique pass then removes every finding it cannot back with the diff, the retrieved code, or a tool diagnostic. It prefers saying nothing over saying something weak.

The dry-run instance was deployed and publicly verified in September 2026, then retired to stop continuous hosting charges. **There is no always-on demo now.** A live session can be reactivated on request; the [deployment walkthrough](https://github.com/momtazularefin/prcritiq/blob/main/docs/deployment.md#reactivate-the-demo) records how. The existing `v0.1.0` tag remains on the tested runtime commit; later evidence and retirement documentation are linked from `main`.

This image is an offline replay at a lower evaluation threshold, not a capture of GitHub comments or the shipped publication setting:

![PRCritiq reviewing django/django#21875: two published findings, three suppressed with their reasons, and the two human-confirmed defects](https://raw.githubusercontent.com/momtazularefin/prcritiq/main/docs/media/review-django-21875.png)

This is one paid, model-assisted benchmark replay of a frozen Django pull-request revision with two human-confirmed defects. The evaluator marked two findings publishable at a threshold of 65, one of which its mechanical matcher credits against a confirmed defect. It also drafted the second confirmed defect but withheld it at 63% confidence. No comment was posted to GitHub; “published” in the image means only that a finding passed the replay threshold. The [raw report and settings](https://github.com/momtazularefin/prcritiq/blob/main/eval/runs/2026-09-24-django-evidence-image/README.md) are kept with the image.

## Run it locally

You need Python 3.12 and [uv](https://docs.astral.sh/uv/):

```bash
uv sync --dev
uv run prcritiq review --repo pydantic/pydantic --pr 13680 --context --tools
```

Add `--review` to draft findings with a model, which needs an API key and spends credit. Add `--post` to publish them, which needs a token and a database. Nothing reaches GitHub without `--post`. See [getting started](https://github.com/momtazularefin/prcritiq/blob/v0.1.0/docs/getting-started.md).

## What is in this release

### Review pipeline

- A strict unified-diff parser maps every patch to hunks and changed line numbers. It rejects a patch whose hunk header disagrees with its body rather than guessing line numbers.
- A guardrail gate decides which files are in scope and records a reason for every skip: generated, lockfile, vendored, binary, oversized, unsupported language, or unsafe path. Python, JavaScript, and TypeScript are reviewed.
- Context retrieval downloads the repository at the head commit, chunks it along real symbol boundaries, and ranks related code by imports, nearby tests, directory siblings, and identifier-aware BM25. Every chunk carries an id and the reason it was chosen.
- Static analysis runs allowlisted tools only. `ruff` is the only one: a repository cannot supply its own binary, no shell is used, the child process gets a scrubbed environment, and every run has a timeout and an output cap. `eslint` and `tsc` are declined with stated reasons, because both would execute or depend on the pull request's own code.
- A seven-node LangGraph workflow (`fetch_diff → guardrail_gate → static_analysis → retrieve_context → reason_and_draft → self_critique → post_or_summarize`) produces typed findings with severity, a confidence percentage, category, evidence, a suggested fix, and source references.
- Self-critique suppresses any finding that targets a line the pull request did not add, cites a source this run never produced, is generic or duplicated, or falls below the confidence threshold. It records a reason for each one.
- Model routing between Claude and OpenAI is deterministic and never falls back silently. Diffs, retrieved code, and tool output reach the model fenced as untrusted data, and every finding is re-validated afterwards, whatever the model was told.

### Run store and posting

- A Postgres run store records each run, its per-file verdicts, tool outcomes, findings (suppressed ones included), and the routing decision. A `UNIQUE` idempotency key means a repeated request resolves to the existing run.
- Runs move one way, `pending → running → summarized → posted`, with `failed` and `skipped` as terminal states.
- Opt-in posting (`--post`) publishes only findings that survived critique. It re-checks each target line just before writing and refuses a comment body already recorded for that run. When nothing clears the bar, nothing is posted.
- Markdown reports list findings, suppression counts with the invalid-line rate, the files that were not reviewed and why, and tool outcomes.
- Optional LangSmith trace linkage.

### GitHub App webhook

- A signed `pull_request` event (`opened`, `reopened`, `synchronize`, or `ready_for_review`) becomes one persisted review run under a key built from installation, repository, pull request, head commit, and delivery. The run executes in the background, and `GET /runs/{id}` reports its status and counts.
- A redelivery of the same event returns the existing run without executing it again.
- Runs read through a short-lived installation token minted from a signed app JWT. If minting fails, the run fails; it does not fall back to another credential.
- Webhook runs are dry-run and never post. Model review on webhook runs is off unless the operator enables it, so a public webhook URL cannot spend model credit by default.

### Deployment

- A two-stage container image runs as an unprivileged user with every capability dropped. It ships the locked `ruff` for static analysis.
- A Docker Compose stack was tested on one small Hetzner server and can be reactivated on request. Caddy provides automatic Let's Encrypt TLS, security headers, and a request-size cap, and it is the only service with published ports when deployed.
- Cloud-init, an environment template, and a deploy script that ships a committed revision only. The script never ships the working tree, so uncommitted files and secrets stay off the server.
- The public surface refuses private repositories by default. The demo is rate limited per client address and can be switched off.
- See [deployment](https://github.com/momtazularefin/prcritiq/blob/v0.1.0/docs/deployment.md) for setup, operation, and teardown.

### Evaluation and verification tooling

- `prcritiq eval` runs the benchmark against frozen fixtures and writes JSON and Markdown reports with recall, precision, invalid-line rate, no-evidence rate, latency, and cost. It includes a confidence-threshold sweep.
- Datasets must be certified before a live run. Every label needs explicit human adjudication and an exact, reachable target on an added line, and matching is one-to-one.
- `prcritiq verify` is an experimental replay that checks saved findings against bounded base and head context. It prepares everything without model calls unless `--live` is given. It never posts and changes no production default.

## Evidence

- **CI:** the `test` job passed on the tagged commit. It runs Ruff lint and format checks and the full test suite against a real Postgres, with model calls mocked.
- **Tests:** 756 pass with Postgres.
- **Hosted deployment, verified 2026-09-22:** HTTPS health answered with a Let's Encrypt certificate, HSTS, and an HTTP-to-HTTPS redirect, and a demo review of a public pull request returned a dry-run report. The server was later retired; these are historical observations, not a currently available endpoint.
- **GitHub webhook, verified 2026-09-24:** a real `pull_request.opened` delivery for `momtazularefin/persistentcontext#16` became run 3 and finished `summarized` in about a second, with 8 of 21 files reviewable and nothing posted. GitHub's redelivery of that same delivery returned run 3 without running it again.
- **Benchmark:** a four-way drafting comparison on the certified smoke set completed 12 reviews for an estimated $0.372 to $0.381 ([comparison](https://github.com/momtazularefin/prcritiq/blob/v0.1.0/eval/runs/2026-09-18-certified-smoke/comparison.md)). A frozen-candidate verifier comparison completed 48 calls for an estimated $0.704518 ([comparison](https://github.com/momtazularefin/prcritiq/blob/v0.1.0/eval/runs/2026-09-20-verifier-comparison/comparison.md)). Both keep every output, including the false and partial claims. Neither selects a production model. A single review of `django/django#21875` for the README image cost $0.0921 and took 30 seconds.

## Known limitations

- The quality targets are unproven. The benchmark evidence is small and is published as it is, with no claim of general accuracy. The publication threshold (`PRCRITIQ_MIN_PUBLISH_CONFIDENCE=78`) is not calibrated.
- Only Python, JavaScript, and TypeScript are reviewed. Files in other languages are skipped with a reason.
- Bundled JavaScript output without a generated marker is treated as source. The first live run counted three identical copies of an esbuild bundle as reviewable, so with model review on, the same bundle diff would be reviewed three times.
- The hosted service was dry-run only, and its GitHub App has read-only pull request access. Posting is available from the CLI only.
- A webhook run interrupted by a restart stays `pending` or `running` and is not retried. The demo's rate limit lives in process memory. Both suited the single-process deployment and no more.
- Posting avoids ordinary repeats within a run, but it is not exactly-once across GitHub and Postgres under concurrency or a crash.

## Security

- PRCritiq never executes pull request code. It extracts repository snapshots with path-traversal, link, file-count, and size checks, and deletes them afterwards.
- Webhooks require a valid HMAC signature. `GET /runs/{id}` returns status and counts, never finding text, diffs, or code.
- Run the public demo with a token limited to public repositories, read-only. The deployment guide explains why.

See [security](https://github.com/momtazularefin/prcritiq/blob/v0.1.0/docs/security.md) for the full posture.

## Requirements

- Python 3.12 and uv for local use.
- Postgres for persistence, posting, and webhook runs. Tested with Postgres 17; a local instance is `docker compose up -d`.
- An Anthropic or OpenAI API key only for `--review`, live evaluation, or live verification.
- Docker with Compose v2 for the deployment.
